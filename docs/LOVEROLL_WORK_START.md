# LoveRoll — Routine courte de ChatGPT Work

**28 octobre 2026.** [Maître](LOVEROLL_MASTER_PROMPT.md) : décisions, priorités et critères. [Suivi](LOVEROLL_SUIVI.md) : seul état courant et preuves. Le cadre « Exécution prioritaire » du maître autorise la relecture ponctuelle et définit la livraison; cette routine en est l'entrée courte.

1. **Reprendre une fois.** Synchroniser `main`, préserver les modifications et travaux concurrents. Lire les `AGENTS.md` applicables, les dernières entrées utiles du suivi, les décisions et exigences du parcours. Examiner les PR/branches qui le chevauchent, puis seulement les différences pertinentes; aucun audit global ou lecture complète de l'historique à chaque action.
2. **Stabiliser le lot.** Suivre l'ordre métier courant, reprendre un lot compatible engagé et fixer résultat utilisateur, IDs, critères de sortie et dépendances dans le support existant. Développer ensemble UI, serveur, droits, états/erreurs et tests. Enregistrer les idées nouvelles pour la suite sauf blocage ou nouvelle priorité explicite. Local si disponible; sinon commit Git multi-fichiers, sans inventer de tests locaux. Une branche et une PR cohérentes, pas de push par bouton.
3. **Un agent principal.** Intégrer architecture, développement, design, couple utilisateur et QA selon l'impact. Le rôle distinct de responsable sécurité reste en pause; contrôles Auth/RLS et isolation maintenus. Pour un lot important, utiliser si disponible une relecture indépendante en lecture seule selon le cadre du maître; seul l'auteur principal corrige. Aucun enchaînement de six agents ou rapports.
4. **Design et fonctionnement.** Nouveau module/refonte approuvée : vérifier tôt un écran réel représentatif avant de généraliser, sans revalider la charte à chaque retouche. UI : vraies interactions, accessibilité, captures et formats touchés selon le [protocole UX/UI](LOVEROLL_UX_UI_AUTONOME_WORKFLOW.md). Jeu/timer/synchro/SQL/droits : résultats serveur, autorisés/refusés, concurrence, reprise et vraie paire A/B quand requise. Catalogue/paiement/fournisseur : scénarios de test autorisés. Studio A/B réel, LR-041 et autres recettes applicables maintenus; un mock ne les remplace pas.
5. **Vérifier utilement.** Tests ciblés après un groupe cohérent, puis tous les checks requis sur le SHA final. Documentation seule : cohérence, liens et demandes conservées. Réutiliser seulement les preuves traçables encore valides (comportement, dépendances, droits, schéma, configuration, environnement); refaire la partie affectée. Verdict réel `UX OK`, `À CORRIGER` ou `NON VÉRIFIÉ`; aucune baseline approuvée pour cacher un défaut. Pas de suite manuelle identique sans changement pertinent, échec ou doute précis.
6. **Livrer jusqu'au résultat.** Push groupé, PR, CI finale jusqu'à conclusion; réparer les causes d'échec sans affaiblir les tests. Pendant l'attente, au plus un travail indépendant sans collision ni changement du SHA en validation. Après deux tentatives identiques infructueuses, revoir la cause. Fusion autorisée puis publication/version/assets/parcours servis vérifiés; distinguer Pages, SQL appliqué, Edge, APK et appareil physique. Un blocage précis ne bloque que ses dépendants.
7. **Passation et poursuite.** Une note par livraison significative : utilisable / manque / PR-SHA et preuves / publication / blocage / prochaine action exacte. Aucun statut applicatif gagné par documentation. Pas de boucle documentation → CI → documentation ni de réaudit sans élément nouveau. Enchaîner les lots autorisés pendant la session sans attendre « Continue »; aucune poursuite après session n'est présumée.

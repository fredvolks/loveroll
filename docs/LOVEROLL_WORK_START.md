# LoveRoll — Routine courte de ChatGPT Work

**28 octobre 2026.** Entrée opérationnelle unique : [maître](LOVEROLL_MASTER_PROMPT.md) pour décisions, priorités et critères; [suivi](LOVEROLL_SUIVI.md) pour état et preuves. Cette routine remplace les répétitions de cadence, sans changer le jeu ni ses protections.

1. **Reprendre une fois.** Synchroniser `main`, préserver les modifications et travaux concurrents. Lire les `AGENTS.md` applicables, les dernières entrées utiles du suivi, les décisions prioritaires et les exigences du parcours. Examiner une fois les PR/branches qui le chevauchent, puis les seules différences pertinentes; aucun audit global ou lecture de tout l'historique à chaque action.
2. **Choisir un parcours complet.** Suivre l'ordre métier courant, reprendre un lot compatible engagé, fixer résultat utilisateur, IDs, critères de sortie et dépendances dans le support existant. Développer ensemble UI, états/erreurs, serveur et tests nécessaires sur une branche. Local si disponible; sinon un arbre/commit Git multi-fichiers, avec limites explicites. Aucun test local inventé, push par bouton ou refonte massive sans lien.
3. **Un seul exécutant.** Architecture, développement, UX/couple et QA sont des regards selon l'impact, sans six agents, rapports ou approbations successifs. Le rôle distinct de responsable sécurité reste en pause selon la décision du 28 octobre; Auth, RLS, isolation A/B et contrôles techniques restent exigés. Délégation seulement si demandée ou prévue par les instructions applicables.
4. **Valider le changement.** Documentation : cohérence, liens, demandes conservées. UI : vraie interaction, accessibilité, captures et formats affectés dans une recette groupée selon le [protocole UX/UI](LOVEROLL_UX_UI_AUTONOME_WORKFLOW.md); élargir pour composants partagés. Jeu/timer/synchro/SQL/droits : règles et résultats serveur, autorisés/refusés, concurrence, reprise et vraie paire A/B isolée quand requise. Catalogue/paiement/fournisseur : contrats et scénarios de test autorisés. Recettes spécifiques du maître maintenues, dont Studio A/B réel et LR-041 pour modifications transversales/audits; un mock ne les remplace pas.
5. **Éviter les répétitions.** Tests ciblés pendant le codage, puis tous les checks requis sur le SHA final. Réutiliser uniquement une preuve traçable encore valide pour le comportement, dépendances, droits, schéma, configuration et environnement; refaire la partie invalidée. Pas de suite manuelle identique sans changement pertinent, échec ou doute précis. Verdict visuel réel `UX OK`, `À CORRIGER` ou `NON VÉRIFIÉ`; pas de Figma/maquette systématique ni de baseline approuvée pour cacher un défaut. Corriger les écarts aux critères; idées facultatives dans la suite.
6. **Livrer jusqu'au résultat.** Push groupé, une PR, suivre la CI finale jusqu'à conclusion et réparer les causes d'échec sans affaiblir les tests. Pendant l'attente, au plus un travail indépendant sans collision ni modification du SHA validé. Après deux tentatives identiques infructueuses, réexaminer la cause. Fusion autorisée, publication et version/assets/parcours réellement servis vérifiés; distinguer Pages, SQL appliqué, Edge, APK, émulation et appareil physique. Un blocage précis ne bloque que ses dépendants; aucun critère non prouvé déclaré terminé.
7. **Passation unique et poursuite.** Une note par lot : utilisable / manque / PR-SHA et preuves / publication / blocage / prochaine action. Pas de boucle documentation → CI → documentation, ni de réaudit du même blocage sans élément nouveau. Enchaîner les lots autorisés pendant la session sans attendre « Continue »; aucune poursuite après session n'est présumée.
